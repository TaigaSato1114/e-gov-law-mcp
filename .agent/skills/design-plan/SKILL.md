# 設計・計画書作成規約

## 目的
ユーザーの「要望」と「現在のソースコード」を深く分析し、安全かつ効率的に実装するための計画（設計書）を策定する。また、実装前の不確実性を排除するための土台を作る。

## 成果物の配置と命名規則

- **配置場所**: `./plan/` ディレクトリ配下に作成
- **ファイル名**: `[設計書]○○.md` を使用
  - ※ `○○` には実装する機能名を日本語で入力（20文字程度で簡潔に記述すること）

## 設計・計画書（成果物ファイル）の基本構成
作成するMarkdownファイルには、以下の要素を必ず含めてください。

1. **機能概要**: 実装する機能の目的とゴール
2. **現在の実装状況の分析**: 関連する既存コード、コンポーネント、ディレクトリ構造の確認結果
3. **実装方針・アプローチ**: どのように修正・追加を行うかの方針をコードベースで記載
4. **作業手順**: 実装ステップのブレイクダウン
5. **影響範囲**: この変更によって影響を受ける可能性がある既存機能やファイル
6. **更新履歴**: 資料の末尾に設置する変更ログ（日付、変更内容、版数を管理する表）

---

## 課される振る舞い・ワークフロー
AIエージェントは、本Skillsが呼び出された際、以下のステップを厳守して行動してください。

### 1. 現状の分析と計画策定
ユーザーの要望を受け取ったら、即座に実装にとりかかるのではなく、まず現在のワークスペースのコードを確認・分析し、どう修正すべきかの計画を練ってください。

### 2. 成果物（設計書）の作成・提出
上記「設計・計画書の基本構成」に従って、`./plan/[設計書]○○.md` を新規作成し、ファイルとして保存してください。その際、**「6. 更新履歴」に初版の記録を必ず記載**してください。

### 3. 提出後の質問・疑問点の出力（最重要）
設計・計画書ファイルを提出した**直後のチャットメッセージ**にて、計画を練る中で自身（AI）が疑問に思ったこと、ユーザーに仕様を決めてほしいこと、懸念点などを箇条書きで出力してください。
> **注意**: ユーザーからこの質問に対する回答を得るまでは、実際のソースコードの修正（実装フェーズ）には進んではいけません。

### 4. 計画の確定とGitコミット（Skill連携）
ユーザーから質問への回答を受け取ったら、必ず `./plan/[設計書]○○.md` を更新して計画をフィックスさせ、**「6. 更新履歴」に変更内容を追記**してください。
計画が完全に固まったら、ユーザーと合意の上で**即座に `commit` Skillを呼び出し、設計書ファイルをGitにコミット**してください。
- **コミット時の注意**: `commit` 規約に基づき、Typeは `docs`、Scopeは `plan`（またはコンポーネント名）を選択すること。
- **次のフェーズへの移行**: コミットが正常に完了したことを確認した後、初めて実際の実装フェーズへと移行してください。
