# コミットメッセージの生成

## 実行手順 (Procedure)
1. 対象となるファイルの変更内容（Gitの差分やステージングされた内容）を注意深く確認してください。
2. 変更内容の要点を把握し、以下の【コミットメッセージ規約】に完全に準拠したコミットメッセージを1行で生成してください。
3. 生成したメッセージをユーザーに提示し、確認を求めてください。（指示されている場合は、そのままコミットツールを実行してください）

## コミットメッセージ規約

### 1. 基本フォーマット
```text
<type>(<scope>): <description>

```

### 2. 重要な記述ルール

* **1行目（ヘッダー）は50文字程度**に収めてください（最大でも60文字以内）。
* 1行目の末尾には句読点（`.` や `。`）をつけないでください。
* 詳細な背景や理由は、コミットメッセージではなくプルリクエスト（PR）側で詳細に記載するため、ここでは簡潔な記述に留めてください。

### 3. 各項目の定義

#### ① `<type>`（必須）

コミットの種類を表すプレフィックスです。以下のいずれかから最も適切なものを選択してください：

| Type | 説明 |
| --- | --- |
| `feat` | 新しい機能の追加 |
| `fix` | バグの修正 |
| `test` | テストコードの追加・修正（backend, frontend等） |
| `refactor` | 仕様変更やバグ修正を伴わない、コードのリファクタリング |
| `docs` | ドキュメントのみの修正・追加（README、インラインコメント等） |
| `chore` | ビルドプロセス、補助ツール、ライブラリのアップデートなど（ソースコード本体やテストに影響しないもの） |
| `ci` | CI/CD（GitHub Actions、Harness等）の設定変更・環境構築 |

#### ② `<scope>`（任意・推奨）

変更が影響するコンポーネントやレイヤーを記述し、どこを修正したかを明確にします。

* 例: `backend`, `frontend`, `harness`, `api`, `db`, `config`

#### ③ `<description>`（必須）

変更内容を**日本語で**簡潔に記述します。

* 過去形（「〜した」）ではなく、「〜を追加」「〜を修正」という形で記述を統一します。

### 4. 具体例

#### 🟢 良い例（Good）

```text
test(backend): ユーザー認証のユニットテストを追加

```

#### 🔴 悪い例（Bad）

```text
fix(harness): テストステージでコンテナが起動するのに時間がかかってたまにCIが落ちちゃう問題があったので、対策としてパイプラインの設定ファイルを開いてタイムアウトの時間を10分から20分へと延長する修正を行いました。

```
