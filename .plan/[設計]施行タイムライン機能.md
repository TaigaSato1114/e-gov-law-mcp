# [設計] e-Gov 法令MCP 施行タイムライン機能

> 目的: 「**法律がいつ施行されたか（施行の最新情報）**」の取得を最優先に据える。
> 本設計は Claude / GPT 両案を突き合わせた収束版（debate 1 ラウンドの合意）。
> 作成日: 2026-07-06 ／ 前提: API v2 実地検証済み（`.plan/api-v2-enforcement-findings.md`）。

---

## 1. 目的と範囲

### 1.1 方針

- **施行の最新情報取得を最優先**とする。
- 汎用の「施行日タイムライン」機能に集中する。

### 1.2 現状の構造的欠落

- 既存 8 ツール（`find_law_article` / `search_laws` / `search_laws_by_keyword` /
`get_law_content` / `batch_find_articles` / `prefetch_common_laws` /
`get_cache_stats` / `clear_cache`）は**すべて「現行版の本文取得」に閉じており**、
施行タイムライン（改正履歴・施行日・未施行/施行済みの区別）を一切扱っていない。
- 本機能はこの欠落を埋める新ツール群を、既存ツールを壊さずに追加する。

## 2. 用語と API 対応（endpoint / param 対照表）

### 2.1 エンドポイント


| endpoint                                               | 役割                                                         |
| ------------------------------------------------------ | ---------------------------------------------------------- |
| `/laws`                                                | 法令一覧・検索（横断候補抽出用）                                           |
| `/law_revisions/{law_id_or_num}`                       | **改正履歴＝施行タイムラインの正典**                                       |
| `/law_data/{law_id_or_num_or_revision_id}`             | 本文取得                                                       |
| `/attachment/{law_revision_id}`                        | 添付ファイル                                                     |
| `/keyword`                                             | 全文キーワード検索                                                  |
| `/law_file/{file_type}/{law_id_or_num_or_revision_id}` | ファイル取得                                                     |
| OpenAPI 実体                                             | `https://laws.e-gov.go.jp/api/2/swagger-ui/lawapi-v2.yaml` |


### 2.2 ★ パラメータ名はエンドポイントごとに違う（重要な確定事実）


| クエリ     | `/law_revisions/{id}`                       | `/laws`                          |
| ------- | ------------------------------------------- | -------------------------------- |
| 施行期日レンジ | `amendment_date_from` / `amendment_date_to` | **無し**                           |
| 公布日レンジ  | `amendment_promulgate_date_from` / `_to`    | `promulgation_date_from` / `_to` |
| 施行状態    | `current_revision_status`（カンマ区切り・複数可）       | —                                |
| 時点指定    | —                                           | `asof=YYYY-MM-DD`                |
| 種別      | `mission`（New,Partial）                      | `mission`                        |
| 廃止      | `repeal_date_from/to`, `repeal_status`      | `repeal_status`                  |
| 軽量化     | —                                           | `omit_current_revision_info`     |


> **制約**: `/laws` には施行日レンジフィルタが無い。全法令横断で直近施行を拾うには
> 「公布日で候補を絞り → 各法の `/law_revisions` を見る」二段の合わせ技が必須。

> **設計ルール**: MCP ツールの引数名は極力 API のクエリ名に合わせる
> （`status_filter` のような独自語は運用時の誤用を招くため使わない）。

### 2.3 `current_revision_status` enum（確定 4 値）


| 値                  | 意味               |
| ------------------ | ---------------- |
| `CurrentEnforced`  | 現行施行中            |
| `UnEnforced`       | 未施行（これから施行される改正） |
| `PreviousEnforced` | 施行済みだが現行ではない過去版  |
| `Repeal`           | 廃止               |


### 2.4 施行関連レスポンスフィールド（`revision_info` / `current_revision_info` / `revisions[]` 共通）

- `amendment_enforcement_date` … **施行日**（YYYY-MM-DD）★これが「いつ施行されたか」
- `amendment_promulgate_date` … 公布日
- `amendment_scheduled_enforcement_date` … 施行日未確定時の予定日
- `amendment_enforcement_comment` … 施行日の注記（例「公布の日から起算して三年を超えない範囲内において政令で定める日」）
- `amendment_law_id` / `amendment_law_title` / `amendment_law_num` … 改正法令
- `amendment_type` / `mission` … 改正種別
- `current_revision_status` … 上記 4 値
- `law_revision_id` … 版ID。構造 = `{law_id}_{施行日YYYYMMDD}_{改正法令id}`
- `current_revision_info` … **asof に依存しない「今日基準の現在以前の最新版」**（API が計算済みで返す）

### 3.4 【P1】`find_recent_enforcements_global` — 全法令横断で直近施行（合わせ技）

```python
@mcp.tool
async def find_recent_enforcements_global(
    promulgation_date_from: str,                 # 必須：候補を公布日で絞る
    promulgation_date_to: str = "", mission: str = "",
    enforcement_date_from: str = "", enforcement_date_to: str = "",  # ローカルフィルタ
    max_laws: int = 100, max_concurrency: int = 8, ctx: Context = None,
) -> dict:
    """公布日で候補抽出 → 各法revisionsを並列検査 → 施行日降順にマージ。"""
```

手順:

1. `/laws?promulgation_date_from=...[&promulgation_date_to&mission]` で候補 `law_id` 列挙。
2. 候補ごとに `/law_revisions/{id}?current_revision_status=CurrentEnforced,PreviousEnforced[&amendment_date_from]`
 を**有界並列**（asyncio.gather + セマフォ `max_concurrency`）。
3. 施行日降順にマージ。`enforcement_date_from/to` はローカルフィルタとして適用。

返却に `candidates_scanned` / `truncated` / `note`（手法の限界＝公布日窓の外で施行される旧法改正は拾えない旨）を明示。
候補過多時は有界並列＋progress イベント＋ハード上限＋`truncated=true`／継続カーソル。

## 4. 施行最新情報の解決アルゴリズム

### 4.1 導出ロジック（共通）

```python
def derive_enforcement_status(rev: dict, asof: date) -> dict:
    st = rev.get("current_revision_status")
    if st == "Repeal":
        return {"enforcement_status": "repealed", "days_to_enforcement": None, "finalized": True}
    d = rev.get("amendment_enforcement_date")
    if not d:                                   # 施行日未確定（scheduled/commentのみ）
        return {"enforcement_status": "scheduled_uncertain", "days_to_enforcement": None,
                "finalized": False}
    ed = date.fromisoformat(d)
    if ed <= asof:                              # 当日施行は施行済扱い
        return {"enforcement_status": "enforced", "days_to_enforcement": None, "finalized": True}
    return {"enforcement_status": "unenforced", "days_to_enforcement": (ed - asof).days,
            "finalized": True}
```

### 4.2 「いま最新施行版」の解決（`get_latest_enforcement_for_law`）

1. `/law_revisions/{id}` を取得。
2. `current_revision_info` があればそれを最新施行版として返す（`source_field="current_revision_info"`）。
3. 無い場合のみ `current_revision_status=CurrentEnforced` の版で解決（`source_field="status_filter_fallback"`）。
4. クライアント側での降順ソートはしない（API の計算結果を信頼）。

### 4.3 as-of 解決（`get_law_text_asof`）★ 討論で最も重要な確定点

```python
def resolve_revision_asof(revisions: list[dict], asof: date) -> dict | None:
    # 1) 状態非依存で enforcement_date <= asof を集める（未来asof対応）
    cand = [r for r in revisions
            if r.get("amendment_enforcement_date")
            and date.fromisoformat(r["amendment_enforcement_date"]) <= asof]
    # 2) 廃止判定: asof が repeal_date 以降なら「有効本文なし」
    repealed = [r for r in cand
                if r.get("current_revision_status") == "Repeal"
                and r.get("repeal_date")
                and date.fromisoformat(r["repeal_date"]) <= asof]
    if repealed:
        return {"no_effective_text": True, "last_enforced": _latest(cand), "repeal": repealed[-1]}
    if not cand:
        return None                              # 制定前 → ネガティブ
    # 3) enforcement_date 降順 → 同日は law_revision_id 降順で最新
    return max(cand, key=lambda r: (r["amendment_enforcement_date"], r["law_revision_id"]))
```

**2 つの決定的な正しさ（討論の合意）:**

1. **`current_revision_info` を過去 asof 本文の根拠に使わない** — これは「今日基準の最新版」で
 asof 非依存。過去 asof に使うと誤答する。as-of 解決は必ず `/law_revisions` の
 `amendment_enforcement_date` で行う。
2. **状態非依存の日付フィルタ** — `enforcement_date <= asof` で選ぶ際、`current_revision_status`
 で絞らない。今日 UnEnforced でも `asof=2027-01-01` なら施行済みとして選ぶべき版がある。
 状態（今日基準）で絞ると未来 asof を誤る。

## 5. データモデル / 返却スキーマ

- **timeline エントリ標準スキーマ**: §3.2 参照。生フィールド（API 由来）＋ `derived`（サーバ導出）で構成。
- **`enforcement_status` enum**: `enforced` / `unenforced` / `scheduled_uncertain` / `repealed`。
- **`finalized` boolean**: 施行日が確定しているか（機械可読。`enforcement_status` enum と両立させる）。
- **`law_revision_id` 構造**: `{law_id}_{施行日YYYYMMDD}_{改正法令id}`。`parse_revision_id()` で分解・検証。

## 6. キャッシュ設計（動的 TTL・スケジューラ不要）

### 6.1 性質の分類


| 分類                            | 性質             | TTL                         |
| ----------------------------- | -------------- | --------------------------- |
| `PreviousEnforced` / `Repeal` | 不変（過去版・廃止）     | 30 日                        |
| `CurrentEnforced`             | 実質不変           | 30 日                        |
| `UnEnforced`（施行日確定）           | 施行日到来で状態遷移     | 動的（下記）                      |
| `UnEnforced`（comment-only）    | 施行日未確定＝当分遷移しない | 12 時間                       |
| `/laws` 候補探索                  | 新着で変動          | 24 時間（JST 00:30 ロールオーバー再検証） |
| `asof_resolve`（過去 asof）       | 不変             | 7 日                         |
| `asof_resolve`（今日/未来 asof）    | 変動             | 6 時間                        |
| ネガティブ（空/404）                  | —              | 1 時間（古い asof は 7 日）         |


### 6.2 動的 TTL（未施行版）

```python
def dynamic_ttl(rev_status, enforcement_date, finalized):
    now = datetime.now(JST)
    if rev_status in ("PreviousEnforced", "Repeal", "CurrentEnforced"):
        return 30 * 86400                        # 不変扱い
    if rev_status == "UnEnforced":
        if not finalized:
            return 12 * 3600                     # comment-only は当分遷移しない → 長め
        # 施行日 JST 03:00 までに再検証（常駐ジョブ不要の動的TTL）
        target = datetime.combine(enforcement_date, time(3, 0), JST)
        return max(300, min(6 * 3600, int((target - now).total_seconds())))
    return 3600
```

> **常駐リフレッシュジョブは採用しない**（運用複雑化）。動的 TTL が施行予定日直前に自然と
> 短縮されるため、未施行→施行の反転検知遅延は最小化できる。
> **「日跨ぎ一括 clear」も採用しない**（キャッシュヒット率を無駄に落とすため。動的 TTL が上位互換）。

### 6.3 キー規約

- 単発: `{endpoint}:{path_id}?{canonical_query}&v={ALGO_VERSION}`
  - `current_revision_status` はカンマ連結を正規化してキー化。
  - `v={ALGO_VERSION}` により導出ロジック変更時に一括無効化可能。
- 横断: `find_recent:{promulgation_date_from}:{promulgation_date_to}:{mission}:{max_laws}` ＋候補 `law_id` 配列のハッシュ。
- as-of: 2 段（`revlist:{law_id}` = `/law_revisions` 生データ / `asof_resolve:{law_id}:{asof}` = 解決結果）。

### 6.4 メタ

- 全レスポンスに `cache: { "source": "network"|"cache", "age_seconds": n }` を付与（透明性・デバッグ性）。

### 6.5 実装

- 既存 3 層 LRU に施行系 2 層を追加:
  - `revision_immutable_cache`（max 300, ttl 30 日 = 過去版/廃止）
  - `revision_live_cache`（max 200, 動的 TTL = 現行/未施行）
  - `asof_content_cache`（max 100, ttl 長期 = 過去 asof 本文、実質不変）

## 7. 例外・境界条件


| ケース               | 検知                                                       | 扱い                                                                                                                                           |
| ----------------- | -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 施行日未確定            | `amendment_enforcement_date` 空、`scheduled`/`comment` あり  | `enforcement_status="scheduled_uncertain"` ＋ `finalized:false, reason:"comment_only"`。`scheduled`/`comment` を**原文のまま**返す。日付フィルタ対象外の旨を `note` |
| 廃止                | `current_revision_status=="Repeal"` / `repeal_status` 有効 | HTTP 200 ＋ `no_effective_text:true` ＋ 最終施行版 ＋ 廃止注記。`include_repealed=False` なら timeline から除外                                                 |
| 未来 asof           | asof が未来日                                                | 状態非依存の日付フィルタで正しく解決（§4.3）                                                                                                                     |
| 当日施行 / 日跨ぎ        | サーバ時刻                                                    | 基準日は `date.today()` を **JST（`ZoneInfo("Asia/Tokyo")`）固定**。`enforcement_date <= asof` で当日施行済扱い。判定基準を `note` に明記                               |
| 同日複数改正            | 施行日同一                                                    | `law_revision_id` 降順で安定ソートし全返却。`get_latest_enforcement_for_law` は `all_on_same_day` オプション（既定 false=先頭のみ）                                     |
| law 未解決           | `smart_law_lookup` が None                                | `ToolError(f"Law '{law_name}' not found")`（既存踏襲）                                                                                             |
| revisions 空 / 404 | HTTP 404 or 空配列                                          | `ToolError` にせず `{"timeline": [], "note": "改正履歴なし（制定時のまま）"}`                                                                                 |
| 候補過多              | `len(candidates) > max_laws`                             | 有界並列（セマフォ）＋ progress イベント ＋ ハード上限 ＋ `truncated=true` / 継続カーソル                                                                                |
| API 400（elm 等）    | 既存の既知問題                                                  | リトライせず明示エラーを透過                                                                                                                               |
| 添付欠落              | `/attachment` が空                                         | `attachments: []` で正常返却（404 は 1h ネガティブキャッシュ）                                                                                                 |

## 8. プロンプト改訂（`prompts/legal_analysis.md`）

末尾に「施行情況の明示」セクションを追加:

- 回答冒頭に**基準日 asof を JST の YYYY-MM-DD で明記**（例「2026-07-06 時点の施行状況では」）。
- **公布日（`amendment_promulgate_date`）と施行日（`amendment_enforcement_date`）を必ず区別**して述べる。
- `current_revision_status` を根拠として日本語で明示（現行施行中 / 未施行 / 過去版 / 廃止）。
- **未確定**（`amendment_scheduled_enforcement_date` または `amendment_enforcement_comment` のみ）は
"未確定" と必ず断り、comment は**原文引用**する。確定日のように書かない。
- 未施行改正がある場合は「現行条文」と「改正後条文（未施行、施行日○○予定）」を**分けて提示**。
- **as-of 本文は `/law_revisions` で解決した `resolved_revision_id` を根拠に `/law_data/{law_revision_id}` で取得**。
`current_revision_info` は「今日基準の最新版」なので**過去 asof の根拠には使わない**旨を明記。
- 同日複数施行は全件を同日に並記し、根拠として `law_revision_id` を併記。

## 付録: 設計上の要点 3 つ（討論の結論）

1. **施行の正典は `/law_revisions` に一本化**し、`enforcement_status`/`finalized` はサーバ側で
 `asof` 基準に導出して呼び出し側の負担を消す。
2. **`/laws` に施行日フィルタが無い制約**は `find_recent_enforcements_global` の合わせ技に閉じ込め、
 限界を `note` で必ず開示する。
3. **キャッシュは「不変（過去/廃止/revision_id 直叩き）＝長期」「可変（現行/未施行）＝動的 TTL」で二分**し、
 常駐ジョブや日跨ぎ一括 clear は使わない。**as-of は `current_revision_info` に依存せず
 `/law_revisions` の施行日で状態非依存に解決**する（未来 asof・過去 asof 双方で正しい）。
